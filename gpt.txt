# ALF-RAG — GPT Handover

## What this project is

`alf-rag` is a general-purpose local book question-and-answer tool.

The ambition is deliberately simple:

```
book + question
    ↓
retrieve relevant parts of the book
    ↓
provide enough surrounding context
    ↓
answer using only that evidence
```

It is **not** intended to become a general-purpose RAG framework or an endlessly optimised retrieval benchmark.

The project should remain runnable on both:

* Bazzite Linux
* macOS

Bazzite is currently the main development/test environment. The Mac version should remain portable and should not depend on the Bazzite environment.

## Application structure

Main application files:

* `app.py` — interactive CLI
* `answer.py` — generates the final answer from retrieved evidence
* `question.py` — handles conversational question interpretation
* `retrieve.py` — semantic retrieval and context expansion
* `chunker.py` — converts books and records structural boundaries
* `documents.py` — discovers books and maps them to processed chunks

Generated book data:

* `documents/`
* `chunks/`

These are data, not application source.

The application currently supports:

* processing EPUB/PDF books;
* selecting processed books;
* asking questions about a selected book;
* optional conversational context;
* semantic retrieval;
* structural context expansion;
* answering from retrieved evidence;
* showing source chunk IDs.

## Current retrieval design

The current retrieval flow is:

```
Question
  ↓
CrossEncoder
  ↓
top 5 semantic chunks
  ↓
find each chunk's structural boundary
  ↓
expand ±2 chunks within that boundary
  ↓
deduplicate
  ↓
provide evidence to the LLM
  ↓
answer
```

Current settings:

```
TOP_K = 5
CONTEXT_RADIUS = 2
```

The important design decision is that we are **not** trying to optimise these values against individual books.

The original problem was simple:

A 500-word chunk can be too small to answer a question properly.

For example, information about Python's `collections` module is spread across several neighbouring chunks. Retrieving one semantically relevant chunk does not necessarily provide enough context.

Structural expansion is a bounded way of recovering nearby context without dumping huge amounts of the book into the LLM.

## What we have actually demonstrated

A concrete successful test was:

```
What happens in "Tommy's Burglar"?
```

The retrieval found the relevant story region and the resulting answer correctly described the story.

The final sources were:

```
1, 119, 120, 121, 122
```

The important point is that the semantic retrieval did not have to identify every relevant chunk perfectly. Once it found the relevant region, structural expansion recovered the surrounding story.

This demonstrates that the current mechanism is useful.

It does **not** demonstrate that retrieval is perfect.

## Structural mapping

`chunker.py` records structural boundaries while processing a book.

It currently recognises reliable signals such as:

* Parts
* Chapters
* Appendices
* certain Roman-numeral section headings

The mapper is intentionally simple and deterministic.

Guiding principle:

```
map reliable structure when the source provides it;
do not invent structure when it cannot be recognised reliably.
```

Do not turn this into a huge collection of book-specific regular expressions.

### Whirlygigs

The mapper correctly found 24 story-level sections, from:

```
I — THE WORLD AND THE DOOR
```

through:

```
XXIV — MADAME BO-PEEP, OF THE RANCHES
```

### Introducing Python

The mapper correctly found:

* Parts I and II
* Chapters 1–22
* Appendices A–E

The Python book was particularly useful for checking the structural matcher because ordinary prose contains many things beginning with "I". The Roman-numeral rule was therefore made deliberately more precise to avoid false structural matches.

## Important lesson about retrieval

Do not confuse retrieval ranking with answer quality.

A CrossEncoder score only measures how strongly a chunk matches the question.

It does not tell us:

* whether that chunk is sufficient;
* whether neighbouring chunks are needed;
* whether the chunk is actually useful to the final answer.

One test of:

```
What does the collections module provide?
```

produced some noisy expanded regions but also found two useful areas:

```
Chapter 10: chunks 106–110
Chapter 11: chunks 114–118
```

The LLM was able to use the relevant evidence and ignore the irrelevant material.

We deliberately decided **not** to keep tuning retrieval based on this one question.

## Testing philosophy

Retrieval is expensive on the Bazzite machine.

A full retrieval test can take approximately **20 minutes**.

Therefore:

**Do not run retrieval tests casually.**

Every retrieval test should answer a specific unresolved design question and have a realistic chance of changing what we do.

We already know:

* the application works;
* structural expansion can help;
* the current architecture is coherent;
* at least one concrete story question works well.

The next objective is to evaluate the actual user-facing book-Q&A experience rather than endlessly optimise retrieval mathematics.

If a concrete failure appears, solve that failure.

If representative questions are answered well enough, move on.

---

## Overall ambition

The long-term goal is a useful personal book tool, not a research project about RAG.

It should eventually make it easy to:

1. add a book;
2. process it reliably;
3. select it;
4. ask natural questions;
5. get answers grounded only in that book;
6. continue a conversation when useful;
7. identify the source chunks behind an answer.

The system should prefer **correctness and traceability over cleverness**.

The LLM should not be treated as authoritative about the book.

It should receive retrieved evidence and construct an answer from that evidence.

If the evidence is insufficient, the correct behaviour is to say so rather than invent an answer.

## Working principles

When developing further:

* keep the design simple;
* do not optimise prematurely;
* solve concrete failures rather than hypothetical ones;
* preserve portability between Bazzite and Mac;
* inspect the current file before editing it;
* avoid speculative refactoring;
* prefer complete, understandable changes;
* commit coherent checkpoints;
* push stable checkpoints to GitHub;
* avoid expensive retrieval tests unless the result could affect a design decision.

The immediate task on Bazzite is to commit and push the housekeeping cleanup.

After that, continue from the existing architecture rather than reopening retrieval unless a real user-facing problem demonstrates that it needs changing.
